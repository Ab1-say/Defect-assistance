# Defect-assistance
研发缺陷协作系统，用于测试，产品和开发人员共同跟踪BUG的处理进度
[design.md](https://github.com/user-attachments/files/31820741/design.md)

研发缺陷协作系统 · 设计说明

## 1. 目标与范围

系统用于测试、产品、开发三个角色共同跟踪一个缺陷从被发现到关闭的完整过程：

- 测试人员：提交缺陷、验证修复、验证不通过时重开、回归重现时重开已关闭缺陷；
- 产品经理：确认缺陷是否成立、评估优先级、指派开发、按版本节奏延期或驳回；
- 开发人员：领取自己名下的缺陷、处理中、提交修复。

本系统是轻量演示实现：用“身份切换”代替账号/登录，用 SQLite 保存数据，无外部依赖，便于本地一键运行和二次讲解。

## 3. 角色 × 状态 × 动作

| 状态 | 可执行动作 | 允许角色 | 说明 |
| --- | --- | --- | --- |
| 待确认 NEW | 确认并指派 | 产品 | 必填优先级 P0-P3 与开发人员 |
| 待确认 NEW | 延期 / 驳回 | 产品 | 驳回必须填写原因 |
| 待处理 OPEN | 开始处理 | 开发 | 仅限被指派的那位开发 |
| 待处理 OPEN | 延期 / 驳回 | 产品 | 驳回必须填写原因 |
| 处理中 IN_PROGRESS | 提交修复 | 开发 | 仅限被指派的开发 |
| 处理中 IN_PROGRESS | 延期 / 驳回 | 产品 | 允许在产品介入后调整节奏 |
| 待验证 FIXED | 验证通过并关闭 | 测试 | 测试是“修复完成”的裁决者 |
| 待验证 FIXED | 验证不通过 | 测试 | 缺陷自动回到待处理，需填写原因 |
| 已延期 DEFERRED | 恢复处理 / 驳回 | 产品 | 排期恢复后重新进入待处理 |
| 已关闭 CLOSED | 重开 | 测试、产品 | 回归复现后重开，需填写原因 |
| 已拒绝 REJECTED | — | — | 终态 |

> 设计约束：状态只有一套；动作不是“谁都能改状态”，而是“谁在什么状态下能触发哪个流转”，权限规则在服务端强制执行，前端只是把可选项展示出来。

## 4. 数据模型

```text
users   演示用户：username / name / role(tester|product|developer) / title

bugs    缺陷当前状态：code / title / description / module / severity(S1-S4)
        priority(P0-P3) / reporter_id / assignee_id / state / created_at / updated_at

events  不可变的流转记录：bug_id / actor_id / action
        from_state / to_state / comment / created_at
```

设计要点：

- `bugs.state` 只保存“当前状态”，最新状态用单行随时可查；
- `events` 是追加式审计日志，每次状态流转都插入一条记录，历史不可覆盖；
- `reporter_id`、`assignee_id` 分别外键到 users，便于查询“谁报的、谁在处理”。

## 5. API 一览

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/users` | 演示用户列表 |
| GET | `/api/bugs` | 缺陷列表（含摘要信息） |
| POST | `/api/bugs` | 测试提交缺陷 |
| GET | `/api/bugs/{id}?as={user_id}` | 详情 + 流转记录 + 该身份可执行的动作 |
| POST | `/api/bugs/{id}/actions` | 执行状态流转（动作名、说明、必要时带优先级/指派人） |

服务端返回 400（参数/规则不满足）、403（角色或指派无权）、404（对象不存在）。

## 6. 关键设计思考

### 6.1 为什么要“有限状态机”，而不是“随便改状态”

缺陷处理本质是流程协作：每一步都有明确负责人和完成标准。如果状态可以被任意角色随意改动，会出现“开发把缺陷标成关闭”“测试发现又被打回”这类责任不清的问题。因此把合法流转收敛成一张规则表（`TRANSITIONS`），让代码只认规则，不认人情。

### 6.2 状态命名体现“谁在等谁”

常见误区是把状态描述成动作结果（如“已解决”），但“已解决”无法表达下一步该谁行动。本系统用“待确认 → 待处理 → 处理中 → 待验证 → 已关闭”表达等待对象：

- 待处理 = 等开发动手；
- 待验证 = 等测试验收；
- 待验证不通过自动回到待处理，而不是“退回开发”这种语义模糊的状态。

### 6.3 把“修复完成”和“缺陷关闭”分离

开发说修好了只是 `FIXED`，只有测试验证通过才 `CLOSED`。这实现了“实现者不验收自己成果”的最小职责分离；验证失败回待处理也保留了“曾修复过、再次失败”的完整上下文。

### 6.4 角色被当作权限的边界

- 产品是缺陷进入开发队列的闸门（确认/拒绝/延期/优先级）；
- 开发只能操作指派给自己的缺陷（`assignedOnly`）；
- 测试是最终验收者；
- 状态的历史不因关闭而丢失，`reopen` 会重新进入主流程而不是伪造一条新缺陷。

### 6.5 审计日志是追加的，不是覆盖的

`events` 只插入、不更新。界面上看到的时间线就是它的投影。将来做报表（平均修复时长、一次修复通过率、验证失败次数）时可以直接基于 events 统计。

### 6.6 服务端校验是唯一事实来源

前端只是把 `allowedActions` 渲染成按钮；真正判断“该身份当前能否执行”在 `apply_action()` 中完成。这样绕过界面直接调 API 也无法越权。

### 6.7 为了可演示做了哪些简化

- 用身份下拉框代替登录鉴权，方便一次跑通三角色；
- 一人可同时拥有多个缺陷，但不做复杂的队列/工时管理；
- 没有做缺陷的重复校验、自动邮件通知、SLA 超时等，这些属于后续扩展而非核心状态机。

### 6.8 可能的扩展方向

1. 接入真实登录与 RBAC（JWT + 组织/项目维度）；
2. 增加“处理人不能验证自己提交的缺陷”“产品不能关闭”等更严格约束；
3. 依据 events 生成时效报表与一次修复通过率；
4. 增加附件、引用/关联缺陷、通知订阅与 Webhook。
